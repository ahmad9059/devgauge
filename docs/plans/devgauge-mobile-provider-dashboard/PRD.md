# DevGauge Product Requirements Document

> Status: **Planning. Provider feasibility validation complete.** At the start of this planning pass, no application, schema, API, or UI implementation existed (`README.md:1`); the repository now also contains these planning documents.
>
> Evidence date: 2026-09-21. Provider contracts and limits change frequently and must be revalidated at each connector release.

## 1. Product Summary

DevGauge is a local-first Expo React Native application that gives developers one place to inspect coding-assistant usage and reset windows for exactly five providers:

1. Claude
2. OpenAI Codex
3. Command Code
4. OpenCode Go
5. GitHub Copilot

The product has three primary tabs based on the supplied layout:

- **Usage:** provider cards with available usage windows, percentages, reset times, freshness, and error states.
- **Connectors:** provider-specific connection, permissions, account identity, support level, refresh, and disconnect controls.
- **Settings:** theme, text scale, notifications, privacy, legal, support, diagnostics, and data deletion.

The visual direction adapts the supplied dark mobile reference rather than copying its commerce content: near-black layered surfaces, warm restrained highlights, rounded cards, strong hierarchy, and a floating bottom navigation treatment. Light mode must be designed as an equal theme, not generated by color inversion.

## 3. Problem Statement

Coding-assistant plans expose incompatible quota models. Some use rolling five-hour windows, some weekly allowances, some monthly credits, and some only billing history. Users currently open several first-party dashboards or CLI commands to understand remaining capacity. DevGauge should normalize what can be normalized without misrepresenting provider data or obtaining broader credentials than necessary.

## 4. Product Principles

1. **Honest data over fake consistency.** Never invent a weekly or monthly limit if a provider does not expose one.
2. **Supported auth over session harvesting.** Use registered OAuth/OIDC, device authorization, or user-created scoped keys. Never extract browser cookies or intercept passwords.
3. **Local-first by default.** Usage snapshots, settings, thresholds, and notification schedules remain on device.
4. **Secrets are not ordinary data.** Credentials live in Keychain/Keystore-backed SecureStore, not SQLite.
5. **Stale is better than blank.** Keep the last successful snapshot and label its age when refresh fails.
6. **Provider isolation.** One connector failure cannot break the other four.
7. **Accessible at every density.** Dynamic Type, screen readers, reduced motion, and platform touch targets are release gates.

## 5. Provider Feasibility Matrix

| Provider | Intended connection | Usage data | Product support tier | Release gate |
|---|---|---|---|---|
| Claude | Vendor-approved OAuth or official partner API only | Consumer plan limits are visible in first-party `/usage`, but no public third-party consumer quota API is documented | **Blocked for automatic consumer sync** | Written Anthropic approval plus documented scopes/endpoints |
| Codex | Vendor-approved OAuth or official partner API only | First-party dashboard and `/status` expose five-hour/weekly state; no public third-party consumer quota API is documented | **Blocked for automatic consumer sync** | Written OpenAI approval plus documented usage/reset API |
| Command Code | User-generated API key or vendor OAuth when available | Five-hour, weekly, and plan allowance data appears available through private/alpha APIs | **Experimental** | Vendor permission, contract tests, remote kill switch |
| OpenCode Go | User-generated Go API key | Official docs define 5-hour, weekly, and monthly limits; current usage endpoint is not documented as a stable public contract | **Experimental** | Vendor confirmation of usage endpoint and polling policy |
| GitHub Copilot | GitHub App user authorization | Documented user/org AI credit and premium request billing usage | **Candidate supported; release-disabled** | Prove GitHub App token compatibility, permissions, and account coverage in Phase 6 |

Important distinctions:

- Anthropic Admin Usage/Cost APIs apply to API organizations, not ordinary Claude Pro/Max consumer limits.
- OpenAI API rate-limit headers apply to API projects, not ChatGPT/Codex subscription quotas.
- GitHub billing usage is primarily monthly/billing-period data and must not be relabeled as a five-hour allowance.
- OpenCode Go documents 5-hour, weekly, and monthly caps, but current consumption access still requires a supported usage contract.
- Command Code usage integration depends on private `/alpha/*` behavior and is not production-stable without vendor agreement.

## 6. Target Users

### Primary persona: multi-provider developer

- Uses two or more coding agents during a workday.
- Wants to route work before a quota is exhausted.
- Values precise reset timing and low-friction refresh.
- Understands provider terminology but does not want five dashboards open.

### Secondary persona: team administrator

- Has access to organization-level GitHub or supported enterprise usage data.
- Needs clear account scope and freshness, not employee surveillance.
- Requires explicit permission and privacy boundaries.

## 7. Core User Journeys

### 7.1 First launch

1. App explains local-first storage and provider support tiers.
2. User chooses system, light, or dark theme.
3. User sees all five providers as disconnected cards.
4. User can continue without creating a DevGauge account.

### 7.2 Connect a candidate supported provider after its release gate passes

1. After Phase 6 proves the GitHub auth/permission path and enables the connector, the user opens Connectors and chooses GitHub Copilot. Before that gate, the same card is visibly release-disabled and cannot start authorization.
2. App explains exactly which GitHub permission and billing data are requested.
3. System authentication browser opens; an embedded WebView is never used.
4. Callback state and PKCE are validated.
5. App stores the credential reference securely and imports the first snapshot.
6. Usage tab displays provider-native labels and data freshness.

### 7.3 Connect an experimental API-key provider

1. User chooses Command Code or OpenCode Go.
2. App opens the official key-management page in a system browser.
3. User pastes a newly created key into a secure native form.
4. App validates the key with a minimal identity/usage request.
5. Raw secrets are never shown again or written to logs/SQLite.
6. UI clearly marks the connector as Experimental.

### 7.4 Claude or Codex before partner access

1. Card explains automatic sync is unavailable through a supported public API.
2. User may open the first-party usage dashboard.
3. User may optionally enter a reset time manually and schedule a local reminder.
4. The app must not claim the provider account is connected.

### 7.5 Usage refresh

1. App refreshes on foreground when cached data exceeds provider-specific TTL.
2. User can pull to refresh or refresh one provider.
3. Successful responses are normalized and stored transactionally.
4. Failed refresh retains prior data with a stale badge and actionable error.
5. `429` honors `Retry-After`; repeated failures trigger backoff.

### 7.6 Codex reset action

The requested one-button reset cannot mean forcing a server-side quota reset. No public reset API is documented. The safe product behavior is:

- Button label: **View usage and resets**.
- Action: open `https://chatgpt.com/codex/settings/usage` in the system browser.
- Optional action: **Remind me at reset** using the known or manually entered reset time.
- Never label clearing local state, starting a new chat, or opening a dashboard as **Reset quota**.
- If OpenAI later exposes partner reset redemption, add it only behind a reviewed capability flag and an explicit confirmation sheet.

## 8. Functional Requirements

### 8.1 Usage dashboard

- Show exactly five provider cards in user-configurable order.
- Show connection/support state: candidate/release-disabled, connected, disconnected, blocked, experimental, expired, rate-limited, and stale.
- Display every available window independently: rolling, daily, weekly, monthly, billing period.
- Display used, limit, remaining, unit, percentage, period start/end, and reset time only when supplied or safely derived from documented rules.
- Show `Last updated`, persisted source (`live` or `manual`), and a derived `cached/stale` presentation state when rendering a stored snapshot.
- Provide pull-to-refresh and per-card refresh.
- Provide skeleton, empty, partial, offline, auth-expired, schema-changed, and rate-limited states.
- Use compact horizontal progress/bullet bars with visible text values; color is supplementary.

### 8.2 Connector management

- Present the five providers and no generic arbitrary-provider connector in v1.
- Explain support tier, data available, auth method, scopes, and retention before connection.
- Support secure key entry for approved key-based providers.
- Support OAuth only through system browser and registered callbacks.
- Test connection before persistence.
- Support refresh, reauthorize, revoke/disconnect, and delete local history.
- Allow a remote/local capability manifest to disable an experimental connector without an app update.

### 8.3 Local notifications

- Threshold notifications at configurable utilization levels, default off. In local-only v1 these are evaluated after foreground/manual refresh and are not real-time background alerts.
- Reset reminders at configurable lead times.
- Permission requested in context after user enables a notification feature.
- Notification copy remains generic on lock screens.
- Local notifications are sufficient for v1; remote push is out of scope unless background server sync is later approved.

### 8.4 Settings

- Theme: system, light, dark.
- Text size: follow system by default; optional app scale presets within accessibility-safe bounds.
- Notification thresholds, quiet hours, and per-provider toggles.
- Privacy policy, provider disclosures, terms, licenses, support, and diagnostics export.
- Clear cached usage, disconnect all, and delete all local data.
- Diagnostics export must redact tokens, keys, cookies, authorization codes, account emails by default, and raw provider payloads containing identifiers.

### 8.5 Offline behavior

- Full read access to cached snapshots and settings.
- Clear offline and data-age indicators.
- Connection and refresh actions queue no secret-bearing requests; user retries explicitly or foreground refresh resumes.

## 9. Information Architecture and Screen Design

### 9.1 Navigation

- Root stack: onboarding, main tabs, provider detail, connector flow, legal/support, diagnostics.
- Main tabs: Usage, Connectors, Settings.
- Bottom navigation has three destinations, always visible on primary screens, and respects safe-area insets.
- Provider detail is pushed from Usage and supports platform back behavior/deep links.

### 9.2 Usage screen

- Compact header: DevGauge wordmark, freshness summary, global refresh.
- Optional summary rail: providers near limit, next reset, offline state.
- Provider card anatomy: official brand mark, provider/plan, status chip, one to three window rows, reset countdown, last updated, overflow actions.
- Do not use oversized radial gauges. Compact bullet/progress bars permit accurate comparison in a narrow mobile viewport.

### 9.3 Connector screen

- Group cards into Available, Candidate/release-disabled, Experimental, and Awaiting provider API.
- Each card explains connection type before the CTA.
- Connection sheets show permissions and data retention in plain language.
- Blocked providers offer first-party dashboard links, not fake login controls.

### 9.4 Settings screen

- Sections: Appearance, Notifications, Privacy & Security, Data, Help, About.
- Destructive controls use confirmation sheets and explicit consequences.
- Font scaling preview shows card/list impact before applying an app override.

## 10. Visual Design Contract

### 10.1 Direction

- Mood: precise developer instrument, calm, premium, low distraction.
- Dark theme: near-black background, charcoal elevated surfaces, warm amber/lime accent used sparingly for actionable or selected states.
- Light theme: warm off-white background, white/soft-gray cards, ink text, same semantic accent roles.
- Typography: IBM Plex Sans for UI and numerals; JetBrains Mono selectively for reset times, percentages, and technical metadata.
- Spacing: 4/8-point rhythm; section tiers at 16/24/32.
- Corners: 16-24 for cards/sheets, 12-16 for controls, pill only for chips.
- Motion: short opacity/elevation transitions; no decorative choreography; reduced-motion renders final state immediately.

### 10.2 Accessibility contract

- Normal text contrast at least 4.5:1 in both themes.
- Meaningful non-text UI at least 3:1.
- Touch targets at least 44pt iOS and 48dp Android.
- Dynamic Type and largest practical system font tested without clipping.
- Screen reader order follows visual order and includes exact values/reset times.
- Progress is never conveyed by color alone.
- Official vector brand assets only; no emoji navigation icons.

## 11. Non-Functional Requirements

| Area | Requirement |
|---|---|
| Startup | Cached dashboard interactive within 1.5s on a mid-range supported device after warm launch |
| Refresh | Provider requests independent, cancellable, timed out, and bounded by concurrency 2 |
| Reliability | One provider parser/network failure cannot prevent other cards from rendering |
| Privacy | No provider password, browser cookie, auth code, or secret in logs/analytics/SQLite |
| Storage | Database migrations are forward-only, transactional, and fixture-tested |
| Accessibility | VoiceOver/TalkBack, reduced motion, large text, contrast, and touch target QA required |
| Observability | Local structured events with redaction; crash reporting opt-in decision required before SDK adoption |
| Compatibility | iOS and Android production development builds; Expo Go is not a release target if SQLCipher is enabled |

## 12. Out of Scope for V1

- Arbitrary providers beyond the named five.
- Sending prompts or executing coding-agent tasks.
- Scraping private web pages or capturing sessions/cookies.
- Importing Claude `.credentials.json` or Codex `auth.json`.
- Forcing or circumventing vendor quota resets.
- Cloud synchronization of credentials or usage history.
- Team surveillance dashboards.
- Purchases or subscription management inside DevGauge.

## 13. Success Metrics

- Connection completion rate per supported connector.
- Successful refresh ratio and median refresh latency per provider.
- Percentage of dashboard visits served from fresh data.
- Notification opt-in and notification-to-open rate without measuring sensitive usage values.
- Crash-free sessions and provider parser failure rate.
- User-reported trust metric: data labels match first-party terminology.

## 14. Key Decisions Requiring Sign-Off

1. **Approve the compliant auth boundary:** no embedded WebView login, cookie extraction, or credential-file import.
2. **Approve blocked launch state for Claude/Codex automatic sync:** first-party links/manual reminders until partner APIs exist.
3. **Approve experimental treatment for Command Code/OpenCode Go:** feature flags, vendor approval, and kill switches required.
4. **Approve a stateless OAuth broker for GitHub if confidential exchange is required:** no remote usage database in v1.
5. **Clarify Codex reset intent:** this plan assumes first-party reset-page handoff, not quota circumvention.
6. **Approve SQLCipher tradeoff:** stronger local cache protection requires development builds/prebuild and excludes Expo Go as the primary runtime.
